# Prompt: Improve ComplySense Knowledge Base, RAG Pipeline, Routing Layer, and Document Access

You are working on the **ComplySense** backend AI architecture. Your task is **not to redesign the existing architecture**, but to strengthen and complete it while preserving all existing functionality.

The goal is to make the Retrieval-Augmented Generation (RAG) pipeline secure, deterministic, metadata-aware, and capable of retrieving precise regulatory references without exposing unauthorized information.

---

## Existing Knowledge Base Structure

The fallback knowledge base must always preserve the following directory structure exactly:

```text
knowledge-base/

    dpdp/
        dpdp.md

    cert-in/
        CERT_IN_Directions.md

    iso27001/
        ISO-27001.md

    ugc/
        UGC_Guidelines.md

    naac/
        naac.md

    nist/
        nist_cisf.md
```

If the system is connected to Supabase Storage, the same logical folder hierarchy must also exist there.

The application should treat both sources identically.

---

# Source Priority

The retrieval order must be:

1. Supabase Storage (Primary)
2. Local knowledge-base directory (Fallback)

If Supabase is unavailable, inaccessible, times out, or returns an error, automatically switch to the local fallback without requiring user intervention.

This fallback should be transparent.

---

# Synchronization Requirement

The folder structure in Supabase and the local knowledge-base directory must remain identical.

The loader should verify:

* folders exist
* expected markdown files exist
* filenames match
* metadata can be parsed
* document loading succeeds

Raise warnings for missing documents but do not crash the system.

---

# Metadata-Based Access Control

Every markdown file already contains metadata at the top.

That metadata is authoritative.

Never ignore it.

Use metadata for:

* allowed user roles
* institution restrictions
* framework
* document visibility
* retrieval eligibility
* document identifiers
* version information
* publication details (if available)

Before retrieval, evaluate metadata.

If the user is not authorized, the document must never be retrieved, embedded, reranked, or passed to the LLM.

Unauthorized documents should effectively not exist for that request.

---

# Routing Layer

The routing layer executes before retrieval.

Its responsibilities include:

* determining which compliance framework(s) are relevant
* filtering inaccessible documents using metadata
* selecting the minimum required documents
* preventing unnecessary retrieval
* supporting multi-framework queries when needed

Examples:

DPDP question
→ route only to DPDP

ISO audit checklist
→ ISO only

NAAC accreditation
→ NAAC only

UGC policy
→ UGC only

CERT-In incident reporting
→ CERT-In only

Questions involving multiple frameworks
→ retrieve only the required frameworks.

Never search the full corpus when routing can narrow the search.

---

# Retrieval Pipeline

The retrieval pipeline should be:

User Query

↓

Intent Detection

↓

Metadata Filtering

↓

Routing Layer

↓

Document Selection

↓

Semantic Chunking

↓

Embedding Search

↓

Contextual Reranking

↓

LLM

↓

Grounded Response

No stage should bypass metadata filtering.

---

# Chunking

Implement semantic/context-aware chunking.

Avoid naive fixed-size splitting.

Chunk boundaries should preserve:

* chapters
* sections
* subsections
* headings
* lists
* tables
* bullet hierarchy

Each chunk should carry metadata such as:

* document name
* framework
* chapter
* section
* subsection
* page number (if available)
* source path
* version

Every retrieved chunk must retain this metadata throughout the pipeline.

---

# Grounded Citations

Responses should identify where information came from.

Whenever possible, cite:

* framework
* document
* chapter
* section
* subsection
* page number

Example:

"According to ISO 27001, Clause 5.2 (Page 18)..."

or

"DPDP Act — Chapter III — Section 8..."

The response should never fabricate citations.

If page information is unavailable, omit it.

---

# Security Requirements

The RAG system must never retrieve unauthorized content.

This includes:

* embedding search
* reranking
* context assembly
* final prompt

Access control happens before retrieval.

No unauthorized chunk should reach the LLM.

# Validation & Testing

Implement automated tests covering both Supabase and local storage.

Tests should verify:

### Document Discovery

* all expected folders are found
* all markdown files are detected
* metadata is parsed correctly

### Routing

Verify framework-specific queries retrieve only the intended documents.

Examples:

* DPDP query → DPDP only
* ISO query → ISO only
* UGC query → UGC only
* Multi-framework query → only relevant frameworks

### Metadata Restrictions

Create tests where:

* an authorized user receives the document
* an unauthorized user does not
* unauthorized chunks never enter retrieval

### Fallback

Simulate:

* Supabase offline
* network timeout
* authentication failure
* missing bucket
* missing file

Ensure retrieval automatically switches to the local knowledge-base directory.

### Citation Validation

Verify every answer references the correct:

* framework
* document
* chapter
* section
* subsection
* page (when available)

### Retrieval Accuracy

Ensure routing selects the correct document in both storage modes.

Results from:

* Supabase
* local knowledge-base

should remain functionally equivalent for identical documents.

---

# Constraints

* Preserve the existing architecture unless a change is necessary.
* Do not remove existing features.
* Maintain backward compatibility.
* Keep metadata as the authoritative source for access control.
* Ensure deterministic routing before retrieval.
* Never expose unauthorized knowledge.
* Keep Supabase as the primary source and the local knowledge-base as the automatic fallback.
* Ensure both storage backends use the exact same directory hierarchy and produce identical retrieval behavior.
* Prefer maintainable, modular, and testable implementations with clear separation of routing, authorization, retrieval, reranking, and response generation.
