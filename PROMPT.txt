Here's what's non-negotiable in a real GRC platform, mapped to what applies specifically to ComplySense's stack and constraints.
1. Multi-tenancy isolation (highest risk in your architecture)

Every query must filter by institution_id at the query layer, not just at the API layer — a missed WHERE clause is a cross-tenant data leak, not a bug.
Row-level security (RLS) in PostgreSQL/Neon should be the enforcement mechanism, not application-code discipline alone. If you're not using Postgres RLS policies per table, that's a real gap — app-layer filtering alone fails the moment someone adds a new query path and forgets it.
MongoDB (control library) needs equivalent tenant-scoping on every collection query — Mongo has no RLS equivalent, so this is 100% application-enforced and needs a single shared query-builder function, not ad-hoc filters per route.
Redis keys must be namespaced by institution_id too, or cache poisoning across tenants becomes possible.

2. Audit trail immutability

GRC platforms live or die on "who did what, when, to what evidence." The audit_logs table (if it exists — you're verifying this) must be append-only — no UPDATE or DELETE permission at the DB role level, not just app-level convention.
Every state-changing action needs an audit entry: control status change, evidence upload/approval/rejection, policy approval, role assumption, incident creation. This isn't optional polish — auditors (real ones, using your Auditor role) will specifically check for gaps in this trail.
Timestamps must be server-generated, never client-supplied, or the trail is falsifiable.

3. Evidence integrity

Evidence files (Supabase Storage) need checksums stored alongside the DB record, so evidence can't be silently swapped after approval without detection.
Evidence should be immutable once approved — a new upload should create a new version, not overwrite. Version history matters for audit defensibility.
Access to evidence download should itself be logged (who viewed what evidence, when) — this is standard in ISO 27001 and NIST SP 800-53 audit requirements.

4. RBAC + segregation of duties

The classic GRC control: the person who uploads evidence should not be the same person who approves it (even if same role in a small team, the system should support the separation for institutions that need it).
Nine roles means the permission matrix is large — this needs to be centrally defined (a single source-of-truth permissions table/config), not scattered if role == checks across routes. Scattered checks are how privilege escalation bugs happen.
Role assumption/impersonation (if Super Admin can view as another role) must itself be audit-logged with start/exit timestamps — you already have this in your notification events list, good sign it's designed in.

5. Data sovereignty (your hard constraint)

Ollama local-only for sensitive data is good — but verify nothing sensitive ever transits to Gemini 2.5 Flash. This needs to be enforced structurally (separate code paths / separate service boundaries), not by convention, since a refactor six months from now could accidentally route sensitive prompts through the wrong LLM call.
Document explicitly, per AI endpoint, which model handles it and why — this itself may need to be part of your compliance posture documentation (ironic but real: a GRC platform should be able to pass its own audit).

6. Framework mapping consistency

Controls mapped to multiple frameworks (DPDp, ISO 27001, NIST CSF, NIST SP 800-53, IT Act/CERT-In, UGC/NAAC) — the mapping table needs referential integrity. A control that's "satisfied" under one framework but the mapping silently breaks for another framework is a correctness bug that undermines the whole product's value proposition.
Framework version tracking: ISO 27001:2022 vs older versions, NIST CSF 2.0 vs 1.1 — controls mapped to a specific framework version need to say so, since requirements change between versions.

7. Notification / SLA correctness

Since this is the piece you're actually building: notifications for overdue tasks, pending approvals, evidence expiry need to be reliable, not best-effort. A missed "evidence expiring in 7 days" notification is a compliance failure for the institution using your product. Consider whether this needs a scheduled job (not just event-triggered) to catch time-based conditions (expiry, overdue) that don't have a discrete triggering event.

8. Data retention & right-to-erasure (DPDP Act specific)

DPDP Act 2023 requires data principal rights (access, correction, erasure) — does ComplySense have any mechanism for an institution to fulfill a data subject request? This is often missed in v1 GRC builds because it's not urgent until it's legally urgent.
Retention policies per data type (evidence, audit logs — note audit logs often need to be retained even under an erasure request, which is a real tension worth documenting explicitly).

9. Export/reporting integrity

CERT-In reports, audit reports — exported documents need to be reproducible and tamper-evident. If two people export "the same" report at different times, and underlying data changed, the export should reflect a point-in-time snapshot, not silently be regenerated from live data without saying so.

10. Frontend-specific

No sensitive data (evidence content, control descriptions with sensitive info) should be cached in browser storage beyond session — check whether any Zustand/localStorage persistence accidentally persists sensitive GRC data client-side.
Every action with compliance consequence (approve, reject, submit) needs a confirmation step — the audit already flagged confirmation modals as partially scaffolded; this isn't UX polish, it's a control against accidental state changes that create false compliance records.
